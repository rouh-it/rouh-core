# Rouh wire protocol

One WebSocket at `wss://<the installation's address>/ws` carries everything: microphone audio up,
spoken audio down, and every piece of text and screen content in both directions.

Binary frames are audio. Text frames are JSON. Nothing else is used.

The one exception is a file the person attaches, which goes up and comes back
down over ordinary HTTP. See "Attached files" at the end.

How the socket closed is said by its close code, and the page reads two of them.
4401 is the server saying there is no sign-in behind the cookie any more, and the page goes to `/login`.
1012, WebSocket's own "Service Restart", is Rouh going down on purpose to start again: uvicorn closes every socket with it when systemd stops the process, as every deploy does, so the page says Evolving until it is back rather than Reconnecting (`CONN_WORDS` in `rouh/static/app/socket.js`).
Any other close, a dead network or a crash among them, is Reconnecting.

## Audio formats

- **Up (browser to server):** raw PCM, 16-bit signed, little endian, mono, 16000 Hz.
  Sent as binary WebSocket frames of 20 ms each (320 samples, 640 bytes).
- **Down (server to browser):** raw PCM, 16-bit signed, little endian, mono, 24000 Hz.
  Each binary frame is preceded by a JSON `audio_start` on the first chunk of an
  utterance so the browser knows which reply the audio belongs to.

Two different sample rates on purpose: 16000 Hz is what speech-to-text wants and
keeps the upload small, 24000 Hz is what the text-to-speech returns and resampling
it on the server would cost quality for no reason.

## Client to server

**Numbered moves (`ask`, `asked`, since 23 October 2026).** Every message that moves a tab to a chat or changes its strip of forks - `hello`, `open_chat`, `new_chat`, `open_thread`, `close_fork`, `fork`, `fork_chat`, `answer_chat`, `detach_fork`, `delete_chat`, `delete_folder`, `delete_object` - carries `ask`, the page's own count of them. `ready`, `chat_switched` and `chats` carry `asked`: the newest `ask` of that tab's the server had handled when it worked out the tab's chat and strip in it. The page moves along a strip and closes a fork at once, by itself, and tells the server after; a message whose `asked` is older than the page's newest `ask` was worked out before that, and its word on which chat the tab is in and its strip is not taken (a `chat_switched` is passed over whole). A list of the chats built on a thread before a close and sent after it laid the closed fork out again, until this.

| `type` | Fields | Meaning |
|---|---|---|
| `hello` | `client`, `chat?`, `tz?`, `strip?` | First message. Server replies `ready`. `strip` is where this tab's strip of forks around `chat` ends, the deepest fork laid out to its right, from its screen or from its address (`?strip=`); the tab lays out exactly that strip again, and a strip that does not go through `chat` is taken as none (`forks.strip`). `chat` is the chat this tab is in: the one on its screen after a dropped socket, the one its address names, or the one it was in before a reload (kept in the tab's own `sessionStorage`). The tab is put back into it, and no other tab is moved. Left out, or naming a chat that is not there, the tab opens on the chat the person opened last, in any tab. A page at the front door sends none. A `session_id` is still accepted and is ignored. |
| `speech_start` | - | The browser's voice detector heard speech begin. |
| `speech_end` | `discard?`, `finish?` | Speech stopped. The server transcribes it and joins it to whatever the person has said and not been answered yet, and the model says whether that is a whole request before it answers any of it (`rouh/turnmarks.py`). With `discard: true` the browser judged it too short to be speech, and the server throws the audio away without transcribing it. With `finish: true` the person pressed Finish, so the whole of it is answered rather than judged. |
| `interrupt` | - | The user started talking while Rouh was talking. Stop everything. |
| `dictation` | `on` (bool) | Dictation on or off. The browser holds the utterance open while it is on, so nothing the person pauses on reaches the server at all; the server is told so that nothing is answered on a clock while somebody is still talking. Switched off, the utterance ends at once with `finish: true` and the whole of it is answered. Echoed back as `dictation`. |
| `text` | `text`, `attachments?`, `answers?`, `steer?` | A typed message. Same effect as a finished spoken turn. `attachments` is a list of ids returned by `POST /attachments/{session_id}`; the files themselves went up over HTTP before this was sent. An id that does not belong to this conversation is dropped and an `error` says how many were. `answers` is on a message sent from the question box at the top of a waiting task's page, as `{task, asked, answer}`: `task` is the task's workspace folder as the page read it off its own canvas, `asked` the question as the box showed it and `answer` what was picked or written. It is written down against that task and this chat before the turn starts (`rouh/answering.py`), and every tab is sent `objects` and `workspace` again, so the task stops being marked as waiting on the person. Sent while an answer is being written in the chat, it does not stop that answer: it waits on the turn and the model reads it at its next step, once the tools it is running come back and before it decides what to do next, and it is written into the conversation there, as one of the person's messages in the same exchange (`Brain._take_steer`). `steer` is the page's own name for it, which comes back in `steer_taken`. If the answer ends before the model reads it, it is the next question. Words said aloud and not yet answered are still a question the model is deciding is whole, and then a typed message stands that turn down and joins it, as before. |
| `dismiss_question` | `task`, `asked` | **Dismiss** on the question box at the top of a task's page: the question closed without an answer. `task` is the task's workspace folder as the page read it off its own canvas, and `asked` the question as the box showed it. Nothing is said in any chat, no job is started and the task itself is left as it is; the dismissal is written down against the task (`rouh/answering.py`), so its page keeps the box folded to one line with the way back to it, and every tab is sent `objects` and `workspace` again, whose rows then carry `dismissed: true` and no longer count the task as waiting on the person. Answering the question afterwards undoes it. |
| `retry` | `root`, `text?`, `tier?` | Answer that exchange again, in the place it already has. `root` is the exchange - one question and the answer to it - named by the number every message of it carries. With no `text` it is the same question asked again, which is the retry button; with `text` it is the question rewritten, which is the edit box. Either way the answer that comes back replaces the one that is there rather than being added to the bottom, and the try it replaces is kept: re-asking used to mean sending the same words a second time, which left the conversation holding the question twice with the old answer in between. Whatever was running in the thread is stood down first, for the same reason a typed message stands it down. The old try stops being live only when the new question is actually written, so a retry cancelled before the model answers leaves the conversation exactly as it was. An empty `text` is refused. With `tier` (`cheaper` or `smart`, the two parts of the tier marker on the line at the top of a reply, `app/turnline.js`; `daily` and `best`, from before 23 October 2026, are read as `smart`) this one answer comes from the chat's use on that tier, with no router, whatever the chat is on, and its `route` says `outcome` `chosen`. Since 4 November 2026 the new try is a branch of the conversation at that exchange: everything said after the old try stays with it, off the screen and out of what the model is sent, and the arrows under the message go back to it (`pick_version`). The page sends a tier press with the words of the question's edit box when that box is open, so the tier answers what was typed there. |
| `pick_version` | `root`, `version` | Step that exchange to one of its tries, which is what the arrows under a message do. It changes the conversation and not only the picture of it: the try that is live is what the page draws and what the model is sent from then on. Nothing is deleted on any path. Answered with `version_picked`, to every tab in the thread. Since 4 November 2026 a try is a **branch of the conversation**: what was said after a try stays with it, so stepping to another try brings back whatever followed that one the last time it was read and takes away what followed the other. When anything but that exchange comes or goes, every tab in the thread is sent `chat_switched` with `redraw` and `focus` instead, and draws the conversation again from the top. A card a try revised is drawn again as the branch now being read has it (`ui`, `in_place`). |
| `card_version` | `card`, `version` | The arrows on a card's head, on a card with more than one version: that card drawn again in place, on this tab only, as that version read (`ui`, `in_place`, with `version` and `versions`). Only looking: nothing is written, and every version stays. |
| `ui_event` | `id`, `value` | The person clicked or typed something on a rendered card. |
| `set_mode` | `voice_reply?` (bool) | Turn spoken replies on or off. Until 18 October 2026 it also took `model`, a model picked for the chat the tab was in; that box is gone, and the model is the chat's tier on the Models page (`rouh/modeldefaults.py`). |
| `ping` | - | Keepalive. Server replies `pong`. |
| `set_orb` | `cfg` | The orb's settings, as this person has them now. `cfg` is only what differs from the approved design - an empty object means everything is at it - and it is saved against the person rather than against the browser, which is what carries it across a refresh, a restart of the service and a second device (`rouh/settings.py`). Sent when a slider is let go of, three hundred milliseconds after the last frame of a drag, and when the panel is closed. Nothing is trusted: the server takes a flat object of finite numbers and refuses everything else, and what each number means and how far it may go is the page's own - `orbSane` in `app.js` clamps every value on the way back in. There is no reply: the page already has what it sent. |
| `chat_model` | `chat`, `choice?` | Cheap, Smart or Auto for one chat, the control beside the composer (`chatkinds.choice_of`, Petar, 8 November 2026). Without `choice` it only asks what the chat is on; with it, it keeps `cheap`, `smart` or `auto` on the chat, or `""` to follow the Models page again (Best is Smart, Balanced is Auto, Saver is Cheap). Over the socket because a tab's messages are handled in order: a choice made and a message sent straight after it reach the server in that order, so the message is answered on the choice. Answered with `chat_model` below. |
| `notice` | `act`, `ids` | Something the person did with notices (`rouh/notices.py`): `seen`, drawn at the top of a page that was in front of them; `later`, pushed up out of the way, to read later; `read`, opened in place or followed by a swipe right; `dismiss`, swiped left. Anything but `seen` means they saw it, so its Telegram copy is not sent. Every tab of theirs is sent `notices` again. |
| `list_tasks` | - | Ask for the background jobs again. Server replies `tasks`. |
| `list_workspace` | - | Ask for the numbered work again. Server replies `workspace`. |
| `archive_task` | `id`, `on` (bool) | Put one of Rouh's own background jobs out of the way, or bring it back. An id the server has no row for - a card left over from before a restart, or the deploy card, which has no terminal behind it and no checkout to leave alone - is dropped instead: the record goes and every tab is sent `tasks_forgotten` for it. That is deliberate. It used to answer `error` and leave the card where it was, so the one row a person most wants rid of was the one row they could not get rid of. Putting one away stops it: a job still running is killed first, down the same path `stop_task` takes, so its tmux window is closed; its checkout is untouched, and `updated_at` is left as it was so the row does not move. A job that has already finished has nothing to stop. Bringing one back starts nothing. Every tab is then sent `task` for that job - carrying `status` and `detail` as well when the job was stopped just now - and the whole `tasks` list. A run of the one program is not archived here: its flag lives in the program, beside the run, and the page asks the program itself over `/one/ws`. |
| `mark_seen` | `kind` (`task`, `run` or `project`), `id` or `ids` (runs only), `deep?` | The person has opened this now that it has finished, so the red dot drawn for it goes off, and so do the dots on the rows themselves. Sent on the press, by the page, because only the page knows what was pressed: opening a task's conversation, opening a step, and opening a run's card are the presses that say it. `deep` is the dot itself being pressed rather than the row: that item and everything under it, which is the only honest way to clear a dot that stands for something further down. Without it a task is that task alone, so it keeps its dot while a step inside is still unseen and the person can see how far down the new thing is. A **project** is always deep - its dot only ever means "something in here" - and clears every task and step below it. What counts as stopped is `objects.STOPPED` - a task that is waiting or done, a run that is waiting, in conflict, done or failed - and work actually going on is deliberately not on that list, so there is nothing to mark about it. A **step** never stops in that sense at all: it is the record of work already done, so what finishes it is its page being written, and `owning._ready_at` is where those two meanings become one clock. The mark is one clock on the row and it survives a restart, a reload and a second device. **Every stop is a new one**: the register clears the mark itself whenever a row moves into a stopped state again (`objects._unseen_again`), so a run that finished, was carried on and finished a second time is a second thing to look at. **Archiving is not sent from here**: a run is archived from three places and all three end at `objects.update_run`, which marks it seen there so no caller can forget to. Every tab is then sent the list the object is on - `tasks` for a run, `objects` for a task, a step or a project. An id the register has never heard of is a no-op and says nothing back. **`ids` is the one of these that is not a press**: landing on the runs page is looking at every run the Runs link's dot was counting, which is one act about a whole column rather than one press on one row, so the page sends the list and the server marks all of them and broadcasts `tasks` once. Runs only, at most 500 at a time (`server.MARK_SEEN_MOST`), `deep` means nothing on it, and it is sent instead of `id` rather than beside it. The dot on a run's own card is drawn from the same mark: it says which run the Runs link was about, and it is put out by opening the run, by pressing the dot, or by putting the run away. |
| `get_state` | - | Ask what this tab is really doing. Server replies `state`, for this tab alone. The page asks when it has had a turn on screen with nothing arriving for it for a few seconds (`watchTheTurn` in app.js): a message that never arrives leaves a Stop control that stops nothing and Rouh's own line lit on the orb, and the server is the only thing that knows whether the turn is real. An answer of `idle` ends the turn on screen; `thinking` or `speaking` keeps it, and counts as a sign of life, so a genuinely long turn is never cut short. A tab answering for itself never changes what the work tree says Rouh is doing as a whole. |
| `get_tree` | - | Ask for the work tree again. Server replies `tree`. |
| `list_chats` | - | Ask for the chats and the folders again. Server replies `chats`. |
| `new_chat` | `folder?`, `task?` | A new conversation, made the active one, and **not written down yet**: a draft, with an id and no row, which the first thing said in it makes into a chat under that same id (filed under `folder` when one was given). Pressing New chat and walking away leaves nothing behind. With `task`, a task's or a subtask's workspace folder, it is **Start chat** on that task's or subtask's page: a new conversation about it (a subtask's page sends the subtask's own folder, never its task's, since 29 September 2026), which is the task's own while the task has none, titled with its number and name and `thread: true`, and otherwise another chat filed under the task, untitled until its first exchange names it and `thread: false`. Asked again before anything is said, it is the same draft. It never opens a conversation with something in it; `open_thread` is what goes back to a task's own. This tab is sent `chat_switched` (whose `chat` carries `draft: true`), and every tab `chats`. |
| `open_chat` | `id`, `strip?` | Put that chat in this tab. `chat_switched` to this tab, `chats` to every tab. `strip` is where the strip of forks laid out with it ends, as an address names it ("" for none beyond the chat's own parents); left out, a chat already on this tab's strip keeps the strip (sliding along it), and any other chat is laid out with only the chats it came from. No other tab's strip changes. A chat that is not there leaves the tab where it was, because a stale button in a tab left open for a day must not move the person into a conversation that does not exist. |
| `peek_chat` | `id` | A chat beside this tab's on its strip of forks, asked for whole so the page can draw its card beside the conversation as the chat itself will be drawn: sliding onto it then finds nothing to redraw (fr_60918f90d0bb). | `answer_chat` | `task` | The question box at the top of a task's page, answered: the chat the answer is about to be sent in. `task` is the task's workspace folder as the page read it off its own canvas. It is **the chat the task already has**, never a new one beside it: of the chats the task holds, the one the newest job about the task was started from, which is where its question was raised, else the task's own conversation, the oldest (`conversations.answer_for_task`). | `note_to_parent` | `chat`, `text` | **Send to the task**, in a subtask's own chat: a decision or a note written against the task the subtask is part of (`rouh/subtasknotes.py`). | `fork` | `from`, `text`, `attachments?`, `root?` | **Send as a fork**: Fork beside Send, or Ctrl+Shift+Enter (Cmd on a Mac). **The shape of the workspace is not changed over this socket.** There is no
message here that makes or moves one of its projects or tasks: the one create
path and the one move path are `rouh/objecttree.py`, and what reaches them is
the task browser's own filing (`POST /api/workspace/filing`, README) and the
`python -m rouh.objecttree` commands. The sidebar had a dialog that sent three
messages of its own - `list_workspace_tree`, `new_object` and `move_object`,
answered by `workspace_tree` - and all four went on 22 September 2026 with the
dialog, at Petar's word, because something else is being built for that.

Binary frames from the client are microphone audio and are only read between
`speech_start` and `speech_end`.

**A pause for thought is not the end of a question.** An utterance is not a
question, it is a candidate one. Each is joined to whatever the person has said
and not been answered yet, and the model reads the whole of it and says whether
they have finished asking before it answers a word of it: it starts every reply
with one of three marks, and after either of the two that mean "not yet"
nothing is said, nothing is shown and nothing is stored, so what they say next
joins the same question rather than following half an answer to it. A clock is
set when that happens - twenty seconds after being cut off mid-sentence, thirty
after only announcing what they were about to say - and pressing Finish, or
sending a line, answers what there is at once. `rouh/turnmarks.py` holds the
marks and the words the model is told about them.

**`speech_start` does not cancel anything.** The microphone opening is not the
same as somebody speaking: a cough, a door or a dryer opens it too. Only two
things end a turn early - an explicit `interrupt`, and a finished utterance that
actually contained words. Cancelling on `speech_start` meant background noise
killed a reply outright, and the only trace was several of the person's messages
in a row with nothing in between.

## The work tree

`tree` carries one JSON object. Every node has the same fields and only `kind`
differs: `root`, `worker`, `subagent`, `tool`. A node is `running`, `done`,
`failed`, `waiting` or `lost`, and `waiting` means a person is being asked
something.

```json
{"id": "root", "kind": "root", "state": "running", "children": [
  {"id": "fe968984", "kind": "worker", "label": "Show running version number",
   "state": "running", "effort": "high", "mode": "self",
   "opened_at": 1788900000.0, "children": [
     {"id": "aa73a53b0f2a", "kind": "subagent", "label": "general-purpose",
      "state": "running", "effort": "high", "opened_at": 1788900004.0,
      "children": [
        {"id": "uvs9NBFYcB", "kind": "tool", "label": "Bash", "state": "done",
         "opened_at": 1788900004.2, "closed_at": 1788900004.4, "ms": 205,
         "children": []}]}]}]}
```

Fields that do not apply are left out rather than sent as null: a tool call has
no `effort`, and a node that is still running has no `closed_at` and no `ms`.

Three things about the timing are worth knowing before drawing it.

**It is pushed at most twice a second.** Tool calls arrive in bursts of tens per
second, so a message per event would be a message every few milliseconds
carrying nearly the same thing. The server builds the tree on a half-second beat
and sends it only when it differs from the last one sent.

**A finished node stays for about a minute, then goes.** The tree is "now" with
a short memory, so something that took 200 milliseconds can still be seen.

**Nothing stays running for ever.** A worker that is killed never sends its
closes, so anything still open under a worker that has stopped is marked `lost`
rather than left running.

## The `ui` spec

Claude calls a `show_on_screen` tool; its argument is passed through unchanged as
`spec`. The browser renders it. Every block is `{ "block": "<kind>", ... }`.

```json
{
  "title": "Tomorrow",
  "blocks": [
    { "block": "stat",  "label": "Meetings", "value": "3", "hint": "first at 10:00" },
    { "block": "table", "columns": ["Time", "What"], "rows": [["10:00", "Standup"]] },
    { "block": "list",  "items": ["Call the bank", "Sign the exhibit"] },
    { "block": "text",  "text": "Markdown **is** allowed here." },
    { "block": "code",  "language": "python", "text": "print(1)" },
    { "block": "chart", "kind": "bar", "labels": ["Mon","Tue"], "values": [3, 5] },
    { "block": "link",  "href": "https://example.com", "text": "Open" },
    { "block": "image", "src": "https://example.com/whale.jpg", "alt": "A humpback",
      "caption": "A humpback whale", "width": 640, "height": 427 },
    { "block": "html",  "title": "Two of them", "html": "<div class=g>...</div><style>...</style>" },
    { "block": "sources", "sources": [{ "url": "https://example.com/rates", "title": "Rates for 2026" }] },
    { "block": "conflict", "id": "cf-b950d2c-2", "question": "Both sides rewrote the page header. Keep the top bar removed, or keep the sidebar's new version of it?",
      "heading": "b950d2c into main", "state": "waiting",
      "sides": [{ "heading": "Your job wrote", "text": "The top bar is gone.", "files": "index.html, +2" },
                { "heading": "Main has since", "text": "The sidebar gained a collapsed rail.", "files": "index.html, sidebar.js" }],
      "options": [{ "n": 1, "label": "Take mine, redo on top", "tone": "good", "means": "..." }] }
  ]
}
```

Unknown block kinds are ignored rather than breaking the page, so the tool schema
can grow without a browser change.

`image` draws the picture itself.
The browser loads it from where it is, with no referrer; a host that still will
not serve it is asked again through `/api/canvas/image?src=...`, which is Rouh
fetching it on its own connection and handing the bytes over (`picture.py`).

`sources` is the list of pages a card was made from, and it is always drawn at
the foot of the card, as one numbered list, wherever the blocks put it.
Its first page is `[1]`: a number in square brackets after anything else on the
card - a list item, a cell, a sentence, `[2]` or `[1, 3]` - is drawn as a small
button that brings that page's entry into view and lights it.
A number the list does not have, `[2026]`, stays the text it is.

Rouh's own words carry theirs as text.
When an answer is written from a web search or a page it read, the server puts
`[n]` straight after every piece the API cited, and a "Sources" line over a
numbered list of links at the end of that response (`rouh/citing.py`).
Both travel in `assistant_delta` like the words and are never spoken, and the
page draws them the same way it draws a card's (`footnotes` in app.js).
A conversation read back later is given the same text, worked out again from
the citations stored with the answer.

`conflict` is a job whose work will not go onto main, and the four ways out of
it (`rouh/conflicts.py`).
It is a block of its own rather than an `html` one for one reason: its four
choices have to be pressed, and an `html` block is drawn in a sandboxed frame
that can reach neither this page nor the socket, so buttons inside one would be
a picture of buttons.
The page draws the number of each choice as its key hint and the digits 1 to 4
answer it from the keyboard, unless somebody is typing.
Pressing one sends `conflict_answer`.
A card is stored like any other, so it comes back off the canvas after a
reload; `conflicts` on the handshake is what says which of them are still open,
and one that is not is drawn as over rather than offering buttons that would
answer a question that is already answered.

`inbox` is the connected Gmail inbox as a card the person works through (`rouh/inbox.py`), and only `show_inbox` draws one: a block the model writes itself has any `inbox` taken off, like `compose` and `ask`.
It carries `query`, `limit` and a `token` the server signed naming whose mailbox it is and which thread hears about it, and no mail at all.
The page asks for the inbox over the socket (`card_inbox`) when the card first comes into view and whenever Refresh is pressed, so it is never a picture of the inbox as it was.
It has three faces, one at a time: the list, newest first with unread in bold and a dot; one message as a page of its own, Back at the top and the bottom and Newer and Older to step through, with what it quotes set off behind a dimmer rule; and the compose form a Reply, Reply all or Forward opens, which is the `compose` card's form with Cancel beside Send.
It is a block of its own rather than an `html` one for the reason `conflict` is: its buttons have to reach the mailbox, and nothing in an `html` block can reach anything.

`people` is a list of people, a row each with `name`, `headline`, `location`, `photo` and `url` (`rouh/linkedin.py`), drawn with a Research button a row when it carries a server-signed `token`, and only Rouh's own tools draw one.
The guests of a meeting (`meeting_people` tool, `rouh/meeting_people.py`) are a `people` block with no token, so no buttons, and two more lines a row: `about`, a line of background, and `note`, where Rouh stands with that guest when it is not simply found ("Not sure which LinkedIn profile is theirs: 3 to pick from on their contact").
A `contact` block that shows a contact as it is, with a number, carries `call` while Call from their contact card is on (`rouh/card_call.py`): each number is drawn as a `tel:` link with Call and Text (`sms:`) beside it, and a press only counts the use with `POST /api/card-call` (`how`, `call` or `text`; no number is sent).
A `contact` block's rows may include `title`, the card's job title, while A contact's job title is on (`rouh/job_title.py`).
A `contact` block may carry `photo`, the address of their face: their iCloud card's picture, else the LinkedIn photo Rouh kept for them, both from `/api/people/<id>/photo` behind the sign-in; without it the initials are drawn.
A `contact` block that says which contact it is also carries `addresses`: every email address of theirs as one list (`rouh/person_addresses.py`), each row its `address`, its `label` exactly as the iCloud card has it, where it comes from (`sources`, `source_said`), its `silo` chip and whether the rule is on the address or its domain (`silo_by`), and for the person's own addresses whether it is a connected mailbox (`mailbox`, `mailbox_said`, and `connect` where Rouh can connect it). The page draws the list in place of the card's email rows (`personaddresses.js`), reads it again from `GET /api/people/<id>/addresses`, and changes a silo with `POST /api/people/<id>/addresses/silo`.
An `email` block may carry `from_photo`, the sender's face when they are a contact with one.

`html` is markup the model writes at the time, for the things the fixed kinds
above have no shape for: a diagram, a timeline, a gallery, two things side by
side.
It is drawn in an iframe with `sandbox="allow-scripts"` and no
`allow-same-origin`, so the browser gives it an origin that matches nothing and
it can reach neither the page around it nor its cookies, and with a
Content-Security-Policy inside it that leaves it style, script and pictures and
takes away fetch, sockets, forms and frames.
Rouh's own colour variables and fonts go in with it, and because a frame has
no height of its own the page inside measures itself and says how tall it is
(`rouh-html-size`), which is what the card is sized to.
The `height` on the block is only where the frame opens, so a card does not
start as a sliver and jump; what the page measures is what it ends up, whether
that is taller or shorter.

Where a card is read is the page's business and not the wire's, for every kind
of block.
At 900 pixels and wider the page moves every card out onto the canvas by itself
as it is drawn, one at a time, leaving a line in its place in the stream that
names it and puts it back on the canvas when pressed; a page loaded over the
canvas is not covered, and a card drawn under one waits in the stream until it
closes.
Below 900 there is no canvas beside the conversation, so every card stays in
the stream, and an `html` page scrolls itself sideways when it is wider than
the frame.
The server sends one `ui` message either way, and which of the two the card is
mounted in is the width of the screen it arrived at and a press, if there has
been one.

## The canvas, and reading it back

Every spec that is drawn is also written to the database, as an `artifact` row
with the spec as its first `artifact_version` (`rouh/artifacts.py`).
The number on the card is in that row's id - card 40 is `card-40` - and it is
what `show_again` takes and what the person says out loud.
It is the same number the card had in `screen_cards`, which is where the whole
screen came from and which the migration carried over one for one.

A card is revised rather than replaced by `revise_on_screen`: that adds a
version and moves the row's `head_version`, and never overwrites what was there.
A card with more than one wears `v2 of 2` beside its number, and `show_again`
takes a `version` to bring an earlier one back.

So the canvas is not the browser's.
The browser reads it back over one HTTP request, which is the only thing on this
page that is not on the websocket: it is a page of history, asked for when the
page opens and again as the reader scrolls back, and it has nothing to do with a
turn of conversation.

```
GET /api/canvas/cards?limit=10&before=41&chat=chat-6f2a1c9b40de
    -> {"cards": [{ ...the spec..., "card_id": 40, "at": 1789004400.0,
                    "version": 2, "versions": 2 }, ...],
        "more": true}
```

Newest first, whole, ready to draw.
The page asks for the first page of a chat's cards the moment its socket says `hello`, for the chat its address names, and takes that answer when the conversation is drawn (`cardsEarly`): until 23 October 2026 it asked once `ready` had come, and the canvas came two seconds after the conversation for an answer the server makes in ten milliseconds.
Each carries `after_message_id`, the message it came after, and, when it was drawn inside an answer, `after_call`, the call whose line it sits under (or `in_answer`), and `placed_at`, when it was last put at the end of the conversation.
The page places it there among the words, exactly where it was while the answer was being written.
Which cards a chat has is which artifacts its owner owns: a thread that is a
workspace task shows what that task owns, a loose one shows its own, and a card
whose owner has been deleted is an orphan on nobody's canvas that its number
still brings back.
`before` is the number of the oldest card the page already holds, and `more`
says whether there is anything older than the last one in this answer.
`limit` is ten by default and fifty at most.
`chat` is which conversation's canvas is wanted, and leaving it out means the
active one: a card belongs to the chat it was drawn in, so switching chats shows
that chat's screen rather than everything Rouh has ever drawn.
The page says which chat it is asking for rather than leaving it to the server,
so a switch that crosses with a request already in flight cannot answer with the
other chat's cards.
The request carries the same session cookie as the page, and a request without
one is refused: the canvas is everything the person has been shown.

Paging by `before` rather than by page number is deliberate.
Cards are only ever added at the top, so "the second page of ten" would be a
different ten cards a moment later, and a reader scrolling back would see one
card twice and miss another.

The words are read back the same way, a page at a time, since 23 October 2026.
`ready` and `chat_switched` carry the last forty rows of the chat and `older`, a
mark for where the rows before them end; as the reader nears the top, the page
asks for the page before and draws it above what is there, without moving the
line being read, and any card that was waiting at the top for its message goes
under it. Until then nothing older than those forty rows could be read back.

```
GET /api/transcript?chat=conversation&before=16625.16626&limit=40
    -> {"chat": "conversation", "transcript": [ ...rows as in `ready`... ],
        "older": "16580.16581"}
```

`before` is the mark, the exchange and the row of the oldest row read, and
`older` is the mark for the page before this one, "" at the beginning of the chat.
`limit` is forty by default and two hundred at most.

```
GET /api/canvas/drawn?chat=chat-6f2a1c9b40de
    -> {"cards": [{ ...the spec..., "card_id": 12, "at": 1789001000.0 }, ...],
        "total": 14}
```

Every card drawn **in** one chat, oldest first, whole: what Cards, on a chat's
three dots, lays out on the canvas side by side.
That is not the same question as the one above.
A chat a task owns shows everything its task owns, and a task can hold several
chats; a card is this chat's when the message it came after
(`after_message_id`) is one of this chat's, or when the chat owns it itself.
At most the newest hundred, and `total` says how many there are in all.

## The workspace, for the canvas's breadcrumb

Three more HTTP requests, for the same reason as the canvas above: they are
pages of the person's workspace read off disk, not turns of conversation.
Every one is read fresh on each request, so a task made a minute ago is in the
breadcrumb's list of tasks and a step written a minute ago is in its task.

The tasks themselves are drawn in the canvas by the workspace's own code, in a
frame. These three are what Rouh's own chrome around that frame needs and
cannot get through the frame's edge: the names and numbers each level of the
breadcrumb reads, the siblings each level offers, and the blocks of a step
Rouh itself filed as a `step.md`.

```
GET /api/workspace/index
    -> {"tasks": [{"rel": "tasks/30.jarvis", "number": 30, "name": "Jarvis",
                   "status": "in-progress", "said": "Jarvis, a voice assistant...",
                   "steps": 39, "changed": 1789000000.0}, ...]}

GET /api/workspace/task?rel=tasks/30.jarvis
    -> {"rel", "number", "name", "path", "status", "step_count",
        "steps": [{"rel", "folder", "number": "30-38", "title", "state",
                   "kind": "markdown" | "page" | "notes" | "empty", "page"}, ...]}

GET /api/workspace/step?rel=tasks/30.jarvis/30-38.the-merged-chat-and-canvas
    -> {"rel", "task", "folder", "title", "state", "kind",
        "blocks": [...the same blocks a card is drawn from...],
        "source": "---\ntask: ...", "source_name": "step.md",
        "page": "tasks/.../index.html" | ""}
```

`said` on the index is that task's own summary, the row's `summary`, which is
kept in the database and nowhere else (`rouh/taskrecord.py`) and which
`_tasks.md` is generated from, and
`changed` is the newer of the task folder's own time and its `AGENTS.md`'s.

`page` is what decides how the canvas loads a step. It is set for a step built
the old way, one folder holding an `index.html`, and the canvas frames that page
exactly as it always did; those are neither converted nor rewritten. It is empty
for a step Rouh filed as a `step.md`, which `/workspace/` will not serve and
the workspace's own index cannot draw, and then `blocks` is what the canvas
draws instead, with the same renderer a card is drawn with. `source` for a step
built the old way is the `.md` beside it, named in `source_name`, and never a
`AGENTS.md`.

These read markdown, which `/workspace/` refuses outright and must go on
refusing: a task's `AGENTS.md` is its whole internal record and must never
leave as a page. So `rouh/steps.py` keeps rules of its own, deliberately
narrower than that route's - `workspace.resolve` first, then `tasks/`,
`archive/` or `examples/` only, nothing hidden at any depth, and a path exactly
two parts deep for a task and three for a step - and none of them serves a file
to anybody. They answer JSON to the signed-in page, behind the same sign-in as
every other address here.

## How busy the machine is

The other thing the page asks for over HTTP rather than over the socket, and for
the same reason: it is not a turn of conversation, and nothing on the server
decides when it should be sent.

```
GET /api/machine/load
    -> {"at": 1789004400.0, "cpu_count": 12, "cpu_percent": 11.4,
        "processes": 354,
        "memory": {"total_bytes": 32212254720, "used_bytes": 4187593114,
                   "free_bytes": 28024661606, "percent_used": 13.0}}
```

`cpu_percent` is the share of the interval since the last time this was asked
that the CPUs spent doing something, out of `/proc/stat`, which is what `top`
shows.
It is deliberately not a load average: a load of 4 means nothing without knowing
how many CPUs the box has, and it can go past the end of any ring drawn from it.

`memory` is the whole machine, and it is the only memory the orb tracks.
Memory in use is memory the kernel could not take back if it needed it: `MemTotal` less `MemAvailable` out of `/proc/meminfo`, the figure `free` gives as total less available, so a warm page cache does not read as full.
There used to be a `program_memory` beside it, what Rouh and the one program held between them, for a third ring inside the memory ring and a `rouh + one` line in the open orb.
Petar had that ring taken away on 11 October 2026 (fr_73b8a5917def), and nothing else read it, so it is no longer collected.

The orb polls this every three seconds while it is on the screen, and only while
somebody is looking at the tab.
One poll feeds every drawing of it, and there are two: the rings round the rim
of the 96 px circle in the corner, and the readout in the bottom-right corner of
the orb opened over the whole screen.
There are two rings, nested outside in, each filling clockwise from twelve
o'clock: `cpu_percent` on the rim, green, orange or red at 50 and 70 per cent;
then `memory.percent_used`.
Each arc is a path drawn as exactly its share of its circle, and never a dash on a whole one: the rings' strokes keep their width whatever size the circle is, and a browser lays a dash on such a stroke out in screen pixels, which drew every ring a quarter longer than its reading on the 80 px circle a phone gets.
The memory ring is thinner and on a scale of its own: baby blue from 0 to 50 per
cent, purple from 50 to 75, red above that, each band flat across the whole of
itself so a third of the box reads the same as a twentieth of it, with the three
per cent either side of a threshold blended so a ring creeping past one changes
colour rather than jumping.
A reading that never arrived is no arc at all.
The orb is in one place at a time, so one of the two drawings is on the screen
at once and the poll stops when neither is.
A reader that cannot be read on this machine comes back as `null` with a line
under `errors` saying why, rather than taking the other numbers down with it,
and the page draws whichever of them arrived.

## Turn lifecycle

```
browser                          server
   |  hello                        |
   |  <---------- ready            |
   |                               |
   |  speech_start                 |   state=listening
   |  ~~~~ PCM 16k ~~~~>           |   speech-to-text, streaming
   |  <---------- stt(final=false) |
   |  speech_end                   |
   |  <---------- stt(final=true)  |   state=thinking
   |  <---------- assistant_delta  |   Claude streams
   |  <---------- tool_start/end   |
   |  <---------- ui               |
   |  <---------- audio_start      |   state=speaking
   |  <~~~~ PCM 24k ~~~~           |
   |  <---------- audio_end        |
   |  <---------- assistant_done   |   state=idle
```

An `interrupt` at any point after `state=thinking` cancels the model stream, the
speech synthesis and any audio still queued in the browser, and returns to
`listening` without waiting for anything to finish.

**A turn belongs to the thread it was asked in, not to the tab that asked.**
Every message above carries `chat`, the thread it is part of, and `turn_id`,
and they go to whichever tabs are looking at that thread when they are sent,
which may be none. Opening another thread, opening a task, and the socket
dropping and coming back do not end a turn: it runs to completion on the
server, its answer is written into that thread's history as it completes, and
the cards it draws belong to the question that asked for them. Coming
back to the thread shows it, and so does a reload. A page throws away anything
whose `chat` is not the thread it is showing, because a switch and a message
cross on the wire.

Only two things end a turn early: the person stopping it, and the next question
in the same thread, which is them talking over their own answer. When one
finishes in a thread that is not the one on screen, that thread is marked in the
rail (`unread` on `chats`) and nothing is said out loud - the voice stops the
moment the tab that asked has moved somewhere else, so an answer landing
elsewhere never talks over what the person is doing now.

**Every turn says it is over.** However it ended - finished, failed, stopped,
cancelled by an `interrupt` or replaced by the next question - the thread's tabs
are told, by `state: idle` while it is still that thread's turn and by
`turn_end` with its number once it is not.
That guarantee is the whole of a bug worth naming: the end of a turn used to be
announced only when it was still the current one, so a cancelled or superseded
turn told the browser nothing, and the Stop control sat on screen red and
pressable with Rouh's own line lit on the orb behind it for as long as the tab
was left open. The browser does not trust it either: a turn
with nothing arriving for it is asked about with `get_state`, and a page that
cannot even get an answer to that settles itself.

The end of the words is not the end of the turn. An answer goes on being spoken
for several seconds after the last of it was written, and Stop belongs to the
person for all of that, so the page keeps the control while the sound it holds
is still coming out of the speaker - and takes it away when that drains, not
when the last byte arrived.

**Stopping a turn** is a different thing, and it is not sent on this socket.
`POST /api/stop` sets a flag against the turn that is running
in the chat its body names, `{"chat": ...}`, which is the chat on the screen
of the tab that pressed it (the chat opened last when it names none)
(`rouh/stopping.py`); the loop reads it before each model call, while a
response is still streaming and before and during each round of tool calls, and
abandons the turn at the first of those it reaches. Setting the flag takes no
locks and waits for nothing, so it answers in a millisecond with the model
still mid-stream. The page kills the audio it has already queued in the same
press rather than waiting for the answer, since waiting is a second and a half
of Rouh talking over somebody who has asked him to stop. What the person is
left with is a `stopped` message, a line in the conversation saying the turn was
stopped, and a session ready for the next thing they say.

The difference from `interrupt` is who it is for. `interrupt` is barge-in: the
person started talking, so their words replace the question. A stop is
deliberate and replaces nothing, so it goes back to `idle` rather than
`listening`, and it is written into the transcript where the next turn will read
it.

## Attached files

A file the person attaches is not sent on the socket.
It goes up over HTTP while they are still typing, and only its id travels with the message.
That is why a twenty megabyte PDF does not hold up anything else on the socket, and why the page can show a progress bar per file.

| Request | What it does |
|---|---|
| `POST /attachments/{session_id}` | One file, as multipart form field `file`. Returns `{id, session_id, name, media_type, kind, size, ts}`. Takes almost anything. Refuses a program by its extension or by its first bytes, a file whose first bytes disagree with a name that claimed a known format, and anything over sixty-four megabytes, each with a sentence in `error` that is shown on the chip for that file. |
| `POST /api/workspace/file` | One file onto a **project**, from the Add files button on its own page. Multipart, with the file in `file` and the project's id in `id`; nothing in the request says where the bytes go, and an id that is not a project's is refused. Answers `{ok, project}` with that project as it stands afterwards, or `{ok: false, error}`. The same store, the same ceiling and the same refusals as the row above: a project's files are attachments under a key of the project's own (`objectindex.files_key`), and are read back at `GET /attachments/project-{id}/{file id}`. With `folder` in place of `id` it is one file onto a **task** or a subtask, from Upload on its own page: the folder is the one Rouh framed, read off its own canvas and never off the page (`taskUpload` in app.js), and the answer is `{ok, file, files}` with the task's files as they stand afterwards. A task's files are attachments under `task-{task id}` (`objectindex.task_files_key`), read back at `GET /attachments/task-{task id}/{file id}`, and one is taken off with the filing action `drop_task_file` (`folder`, `file`), which answers `{ok, did, files}`. |
| `GET /attachments/{session_id}/{id}` | The file itself, for the thumbnail in the transcript and for opening it full size. Only png, jpeg, gif, webp, pdf and plain text come back with their own type and `Content-Disposition: inline`; everything else, an uploaded `.html` or `.svg` included, comes back as `application/octet-stream` with `Content-Disposition: attachment`, `nosniff` and a sandboxing `Content-Security-Policy`, so nothing uploaded can ever run as a page on this address. `?download=1` asks the browser to save it instead. |

Both need the same signed cookie the page does.

`kind` is what decides how the file reaches the model, and it is the only thing anything downstream branches on.

| `kind` | Formats | What the model is given |
|---|---|---|
| `image` | png, jpeg, gif, webp | An image content block. Rouh can look at the screenshot. |
| `pdf` | pdf | A document content block, the whole file, plus a line saying it was sent whole and where it is on disk. |
| `text` | txt, md, html, htm, csv, tsv, json, xml, svg, rtf, and every source and configuration format in `CODE`; plus anything whose bytes read as text | The text itself, cut at 40,000 characters with a note saying where the rest is. |
| `file` | doc, docx, xls, xlsx, ppt, pptx, odt, zip and the other archives, mp3, m4a, wav and the other recordings, video, heic, and anything else whose bytes are not text | The name, the media type, the size and the path on disk, to hand to a job that can open it. Nothing in this process can. |

The path on disk is never sent to the browser.
The model is told it, because a job may have to open the file; the page has no use for it.

What the transcript holds is a marker, `{"type": "attachment", "id", "name", "media_type", "kind", "size"}`, not the file.
The marker is expanded into the blocks above just before a request goes out, newest first, until 20 MB of files have been put in one request (the API refuses a request over 32 MB, and base64 is four bytes for every three).
Anything past that becomes a line of text naming the file instead, so a conversation with a dozen screenshots in it keeps working and the newest one is always the one that arrives.
One file may be larger than that whole budget - the cap on an upload is 64 MB - and such a file is stored, kept in the transcript and named to the model with its path, rather than refused on the way in.

`ready` carries those markers back as an `attachments` list on each transcript entry, so a reloaded page draws the same chips and thumbnails.

A marker may carry `made`: a file Rouh made or pointed at rather than one the person handed over.
`made.kind` is `drawn` for a picture a provider drew (with `by`, `model`, `prompt`, `shape`, `quality`, `width`, `height`, `set`, `index`, `of`, and for a change `from`, `area`, `variation`, `mask`), `area` for the small picture of the area painted to change one, and `ref` for a picture named again as the one asked about.
The page draws `drawn` markers as a set of pictures, and the other two as the picture itself rather than as a file.
Such a marker, and any marker at all in Rouh's own message, reaches the model as a line of words saying what it is, never as the picture: a picture Rouh drew is on the person's screen and the words it was drawn from say what is in it (`attachments._made_block`).

## The relay: a Rouh's phone address

Not the page's socket: what a Rouh says to the birth service's relay to be reached from a phone (`rouh/relay.py`).
The service's side (frps, its checks, the claim endpoint, the traffic meter) is not in this repository.
Every address below is a setting: `ROUH_RELAY_URL` is the folder the two calls are under (rouh.land's relay unless an installation names its own).

### The claim, at birth

`POST <ROUH_RELAY_URL>claim`, made once a Rouh is born Connected, and again from Settings when it did not get through.
An "On its own" Rouh never makes it.

```json
{"v": 1, "public_key": "<base64 Ed25519 daily key>", "name": "Still Heron", "tag": "abcd",
 "birth": {"statement": {"birth_key": "...", "name": "...", "tag": "..."}, "signatures": {...}},
 "changes": [], "owner_email": "ana@example.test", "rouh_version": "<build>", "rotate": true}
```

It is signed with the daily key the way the Gene Pool's requests are (`genepool._sign`): `X-Rouh-Time` (Unix seconds), `X-Rouh-Nonce` (32 hex), and `X-Rouh-Signature`, base64 Ed25519 over `POST\n<path>\n<time>\n<nonce>\n<sha256 hex of the body>`.
The service works the name out of the birth key (`rouh/names`) and refuses one that does not match; `birth` and `changes` tie the daily key to the birth key after a rotation; `rotate` is sent only to ask for a new pass.

The answer, 200:

```json
{"v": 1, "state": "granted", "hostname": "still-heron.rouh.page", "https_port": 443,
 "relay": {"server_addr": "relay.rouh.page", "server_port": 7000, "user": "still-heron",
           "token": "<the pass>", "server_name": "relay.rouh.page", "ca": "<PEM>", "auth_token": ""},
 "limit_bytes": 53687091200, "usage_url": "https://.../usage"}
```

`token` is the pass the relay's Login and NewProxy checks hold the Rouh to; `pass` and `secret` are read as the same field.
`ca` is the relay's own certificate authority, the only one frpc trusts for the line to the relay, under the name `server_name`.
`auth_token` is frps's shared `auth.token`, empty when the relay uses none; `https_port`, `limit_bytes` and `usage_url` may be left out.
Or `{"v": 1, "state": "pending", "said": "<one sentence>", "retry_after": 60}`, and the Rouh asks again later.
An error is 4xx with `{"error": "<one plain sentence>"}`, shown to the owner as it is.

### A name of the owner's own (since 10 November 2026, task 140, step 140-13)

A Connected Rouh may take a second address, chosen by its owner (`petar.rouh.page`), beside its born one, which keeps working for good.

- `GET <relay URL>name?name=<n>`, unsigned: `{"v": 1, "name": "<as rouh.land writes it>", "available": true|false, "why": "<one sentence, '' when available>"}`. rouh.land is the judge: taken, kept for itself, other companies' or Rouh's own names.
- `POST <relay URL>name`, signed as the claim is, `{"v": 1, "public_key": "<daily key>", "name": "<n>"}`; `""` gives it back. The answer is the claim's granted answer plus `"chosen": "<name>.rouh.page"` (or `""`) and `"aliases": [...]`; the claim's own answer carries the same two keys from then on.
- `POST <relay URL>address-letter`, signed, `{"v": 1, "public_key": "..."}`: rouh.land emails the owner's account the Rouh's addresses; `{"v": 1, "sent_to": "<masked email>"}`.

The Rouh keeps `chosen` and `aliases` beside `hostname`, opens both names in frpc (port 80 for all; https for the names its certificate covers), gets one Let's Encrypt certificate for all of them, and opens the chosen one once that certificate covers it.

Since 12 November 2026 (task 176, step 176-29) the setting up of a chosen name is watched, so the screen that waits on it never freezes:

- Before Let's Encrypt is asked for a name the certificate does not cover yet, the Rouh asks for the name itself through the relay's port 80 (a probe token of its own on `/.well-known/acme-challenge/`), every 5 s, so a name the relay does not route yet costs no failed check there; after a minute of misses it asks anyway.
- A certificate try for a name chosen in the last 15 minutes that fails is tried again after 10, 20, 40 s and then every minute, not after the 15 minutes and more that renewals wait.
- Once the certificate covers it, the Rouh asks `https://<chosen>/healthz` from outside every 5 s until it answers as this Rouh.
- Rouh's setup API (`/setup/api/state`, Rouh for Mac's) carries `name_progress`: `{"state": "none"|"working"|"ready"|"failed", "name", "address", "since", "until", "said", "detail"}`. `ready` is the certificate covering it and the check from outside passing; `failed` is not ready 180 s after it was chosen (the Rouh goes on trying); `said` is one plain sentence and `detail` the technical part, for Show details only.
- `POST /setup/api/name` answers at once. The name it already has, or `{"do": "again"}`, is Try again: the setting up and its 180 s start over, and rouh.land is not asked again. A press while a name is being taken answers the state with a `notice`, never a second claim.

### frpc

Started the moment the claim is granted, at birth (since 8 November 2026; before, only when the owner pressed Reach me from my phone), and kept off only once the owner turns it off, with frp's client of the version `rouh/relay.py` pins (and the base image carries).
`user` is the label, `metadatas.token` the pass, the token and the pass read from frpc's environment and never written to its file; `loginFailExit = false`, so it reconnects by itself, with a heartbeat every 30 seconds.
Two proxies, both `customDomains = [<hostname>, <the chosen name, if any>]`:

- `http`, type `http`, to Rouh's own web server, for Let's Encrypt's HTTP-01 check; Rouh sends everything else on it to https.
- `https`, type `https`, whose `https2http` plugin unlocks the traffic on the Rouh's side with its own Let's Encrypt certificate and hands it to Rouh's web server. The relay routes it by the name in the TLS hello and never holds a key that unlocks it.

Both set `X-Rouh-Relay` (a mark of this installation's) and the forwarding headers over whatever a visitor sent, which is how Rouh knows a request came from outside: the first-run pages and the internal addresses answer it 404.

### The traffic

`GET <usage_url>`, signed the same way over an empty body, with `X-Rouh-Key: <base64 daily key>`.
`{"v": 1, "month": "2026-10", "bytes": 12345678, "limit_bytes": 53687091200, "slowed": false}`; anything else, or no `usage_url`, and Settings shows no traffic line.
