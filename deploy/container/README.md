# Rouh in containers

Rouh's own container images and the Compose stack that runs them: work package WP9 ("one-command start") of step 98-05, built to step 98-06's requirements, so that Rouh for Mac (step 98-19) and any Linux machine can run the real Rouh rather than a stand-in.
Built and tested on 20 October 2026 (run a914e492).

## Rouh's code is the person's (23 October 2026)

Petar, 23 October 2026: Rouh for Mac must update correctly, but "latest" now means only patch-level fixes to what Rouh runs on, and those go in by themselves; everything else - features, Rouh's own logic, its own security fixes, big library upgrades - reaches a Rouh only as genes, because each user's Rouh changes its own code and a pull must never overwrite it.
Until that day `rouh-core` and `rouh-workers` carried Rouh's code in `/opt/rouh` and ran it from there, so every pull of a newer image replaced the whole of it (and `rouh-keyproxy` carried `keyproxy.py` the same way).
Now the repository is still one codebase; only the packaging is split:

- **`rouh-base`** (`Dockerfile.base`) is what "latest" points to. It holds Linux (`python:3.12.x-slim-trixie`), the apt packages with every Debian security update there is at build time, Debian's Chromium for the headless browser, Node with Codex and Playwright MCP, and the Python libraries of the line's pinned lock. **No Rouh code**: `check-image.sh` refuses a base with any. It is tagged by patch level, `<line>.<patch>` (1.0.0, 1.0.1, ...), with `:<line>` and `:latest` beside it.
- **Rouh's code is the code volume**, mounted at `/code`: a git repository that is the person's own. Since 24 October 2026 a Rouh's first start fetches the newest commit of main that passed its tests (`code-install`, `guard/bin/rouh-code-install`): free, with no account, the commit named by rouh.land's signed record or else by the signed release, its tarball from the public rouh-it/rouh-core on GitHub; an install code, since 8 November 2026, is an optional extra and commits it as the first commit; from then on no pull, image update or restart writes to it, and only genes and the Rouh itself change it, each change through the protected core's change step. The core runs `/code` (writable, its own); the worker mounts it read-only; the key proxy not at all. (Until that day `code-init` copied it from a code image, `rouh-code`; both are gone.)
- **Libraries a Rouh adds itself** (through a gene) go into the extra volume at `/extra`, with `rouh-extra-pip`.

### The decisions, each with its reason

- **One base image for the core, the key proxy and the worker.** They are kept apart by their containers, users, volumes and networks, which is where the separation always was; one image is one thing to patch, to check, to pull and to point "latest" at. The core's container still runs no browser and no one else's code: having Chromium on its disk is not running it.
- **The key proxy runs from the protected core's own image** (`rouh-guard`, since 24 October 2026). Until then it ran `keyproxy.py` from `/code`, which the core can write, so a changed proxy would have run at the next restart.
- **The code a new install starts with is main's newest that passed its tests** (since 24 October 2026; until then the line's cut). Libraries it needs that its base line does not have go into `/extra` at that first start, held to the base's pins. Newer code reaches an existing Rouh as genes; an existing Rouh never moves to another line by itself. Since 11 November 2026 it can also take the newest release of Rouh's code, by itself (Ride along) or on a press, with its own changes kept on top and the result checked by its protected core like any change (README.md, "Rouh's updates"; `rouh/code_update.py`); no image update ever writes `/code`.
- **An existing install keeps its code**: `code-install` leaves a `/code` that is a git repository exactly as it is. If `/code` holds anything that is not a git repository it refuses, with one sentence, and changes nothing; an install that stopped half way is started again (a marker file, and `.git` moved in last).
- **The extra environment is a `pip --prefix` tree per Python minor version in the extra volume, named by a `.pth` line read after the base's own site-packages.** The base's venv is replaced whole by every base update, so nothing added may live there. A second venv cannot be layered: venvs do not chain, and one made "with system site packages" sees Debian's Python, not the base's venv. The `.pth` order means a library the base keeps patched always wins over an extra copy, and every install is held to the base's own pins (`/opt/rouh-base/constraints.txt`). A gene that needs a newer minor of a base library needs a new line, which is a gene's business too. The check runs with `/extra` mounted, so a base that would break an extra library is not switched to.
- **Debian's Chromium, not Playwright's own build.** trixie-security carries Chrome's security releases for Intel and Arm alike, so Chromium is patched by the same apt upgrade as everything else; Playwright's own build moves only with Playwright, whose 0.0.x MCP versions promise nothing between releases. The one program points Playwright MCP at it (`ONE_PLAYWRIGHT_MCP`, `ONE_PLAYWRIGHT_CHROMIUM`, `one/asuser.py`), and the check opens a page with it over MCP.

## The nightly patch job

A row of Rouh's own scheduled work on Clockwork, "Nightly base image patch check", daily at 00:40 on the owner's clock, on the Creator Rouh only (the maker's own Rouh, the one that makes Rouh's releases; `rouh/base_patches.py`). No Rouh instance - every other Rouh - has it.

The exact versions a base is built with are in main, `deploy/container/base/` (its README says what each file is), since 30 October 2026, so one commit of main holds both the code and the versions its images are built with, and a release names that commit with a tag, `base-<level>`.
They are there rather than at the top of the repository because they are the base image's, beside `Dockerfile.base`, which installs them, and apart from Rouh's own `pyproject.toml` and `uv.lock`, which genes move on and the base does not follow.
Until that day they lived on a branch of their own, `base`, which this job pushed to and `base.yml` built main's code from; that branch is kept, read-only, as `archive/base-branch-until-2026-10`, and nothing reads it.

1. **Looks** (`base_patch.py look`, over main's version list): every pinned Python library (`uv lock --upgrade-package 'name<next minor'`, one at a time, kept only when the whole lock moved by patch levels alone, so Django stays on 5.2.x), the `python:3.12.x-slim-trixie` base, Node, Codex, Debian's security updates and Chromium's security releases (against the Debian packages of the published level, read out of its image, which anyone may pull). Same major and minor, newer patch, never anything else; a 0.0.x version never moves by itself. The database image is looked at too, its digest pinned, and PostgreSQL counted major.patch: 18.1 -> 18.2 is a patch, 18 -> 19 is left for genes. Everything newer than a patch is listed and left for genes. Library patches alone wait for the week (boto3 has one nearly every day, and each level is a download on every Mac); a security update, or a Python, Node, Codex or PostgreSQL patch, goes the same night.
2. **Opens a pull request on main.** The next level is committed on top of main on a branch of its own, `base-patch/<level>`, and pushed with the git key the Creator Rouh already has. That starts `.github/workflows/base.yml`, which puts the branch on top of main as it is, refuses a level that is not newer than main's or is already tagged, and opens the pull request, which shows every version that changes. Its tests are the build on GitHub's Intel and Arm runners: the base and the protected core, `check-image.sh` on both, then the whole check with the newest tested commit of main (`guard/bin/check-base.sh`: the line's pinned PostgreSQL, thrown away after, no network, `rouh-check` - the base's parts, the headless browser over MCP, the frozen security checks and the Rouh's own checks).
3. **Merges by itself only if everything passed on both**, by moving main forward to exactly the commit that was tested (never a merge or squash commit, which nobody tested); GitHub then shows the pull request merged. If main moved on meanwhile, the level is put on top of it and checked again, up to four times.
4. **Publishes that commit:** it is tagged `base-<level>`; both packages are checked to be pullable with no sign-in; the image tags move to the digests that were checked; the release of format 2 is signed, held by `mac_release.py release-matches` to the tagged commit (its checkout, stack file, allow-list, stack check and images), and sent to rouh.land, whose `/mac/release/<line>.json` is then "latest" for that line and which refuses an older release. The level's records go on its GitHub Release, `base-<level>`: how the check went on each platform (`result.json` and both logs), what was published (`published.json`), the signed release (`release.json`), `plan.json`, and every Debian package in each image with its `base.env`.
5. **If anything fails**, nothing is merged, tagged or published, and "latest" stays where it was. The pull request stays open, labelled `base: failed`, with a comment saying which job and step failed; the run keeps the same as an artifact; and the ref `refs/base-failed/<level>` says it for the Creator Rouh, whose job reads git only. The job tells the owner once with a notice (Rouh's own channel; notify_owner is how a worker asks Rouh for the same). The next night starts again from main, which only ever holds a level that passed, so the level is tried again under the same number, on the same pull request. A publish that fails after the merge (rouh.land unreachable, say) leaves main at a level with no tag: **Re-run failed jobs** on that run publishes it from the same commit, with the same digests.

The open pull requests (`head:base-patch/`) say what is being tried; https://github.com/rouh-it/rouh-core/releases says every level published, from base 1.0.0 on (the records of 1.0.0 to 1.0.4 were copied there from the old branch on 30 October 2026).

## Rouh for Mac's releases

Rouh for Mac (`rouh-it/rouh-mac`) carries no image addresses of its own. From 0.3.3 it follows **base releases**: `https://rouh.land/mac/base/stable.json` for a Rouh with no base yet, then its own line's `https://rouh.land/mac/base/<line>.json`, each signed with Ed25519 and naming the base, the code image and PostgreSQL by digest, with the stack file. It pulls a newer level beside the running one, runs `rouh-check` on it in a throwaway container with the Mac's own `/code` mounted read-only (`StackUpdater.check`, the same steps as `check-base.sh`), and switches only if it passes; if not, Rouh stays where it is and the menu says what failed in plain words. The release before is kept, images and all, so going back is one press. It never touches `/code`.

Apps before 0.3.3 read only `https://rouh.land/mac/stack/stable.json`. Its last release is the **bridge** (`base.yml` with `bridge`): the new layout under the image names those apps check for (the code image as `rouh-core`, the base as `rouh-workers` and `rouh-keyproxy`, the same digests), so an old app moves itself onto `/code` with its usual pull, start and health check. No stack release follows it: an old app would switch without the check.

The bridge's images, `rouh-core`, `rouh-workers` and `rouh-keyproxy`, were built by `rouh-it/rouh`, the code's repository until 21 October 2026, and are not built any more: that repository was archived on 27 October 2026 (task 140), its nightly "Container images" workflow with it. The packages stay, private, because an app before 0.3.3 still pulls them. Delete them only after those apps have moved on. Since `rouh-guard` is public, rouh.land's gate for the Mac app's updates (`rouhit/mac_app_gate.py`, in `rouh-it/rouh-it-site`) lets every Mac in with no sign-in (checked 30 October 2026: the appcast answers 200 with none).

- **The key.** The private half is the secret `ROUH_MAC_STACK_SIGNING_KEY` of the GitHub environments `release-signing` (base.yml's publish; main, `base-patch/*` and `base-*` tags only) and `code-pass-signing` (Tests on main; main only), never a repository-wide secret, and a file on the signing machine, readable by root only (`ROUH_MAC_STACK_SIGNING_KEY_FILE`, by default `/root/.config/rouh-mac-stack/signing-key.pem`); never on rouh.land's server. The public half is in `mac_release.py` (`PUBLIC_KEYS`), rouh.land's `rouhit/mac_stack_views.py` and Rouh for Mac's `StackRelease.swift` (in `rouh-it/rouh-mac`); change the three together.
- **What is live, and going back.** On the signing machine, from this folder: `python3 mac_release.py base-status`, `base-list`, and `sudo python3 mac_release.py base-rollback <number>`, which publishes that earlier level again as a new, newer release.

## How the parts are kept apart

- **Five networks.** `db` (PostgreSQL and the core), `workers` (the core, the key proxy and the worker) and `browser` (the core, the key proxy and the browser) are internal, with no way out. Only the key proxy is on `egress` and only the core on `edge`, which is also where the page is published, on 127.0.0.1 only.
- **The keys volume** is mounted by the core and, read-only, by the key proxy. The core's start keeps the Anthropic and OpenAI keys there (group `keys`, mode 0440; the core's own user is in `keys`, so a key given on Rouh's page lands in that group too) and makes the encryption key there once (the core's own user only, mode 0400). The proxy runs as `keys` and so reads the two model keys and not the encryption key.
- **The worker holds no key.** Its environment has none, it mounts no key, it cannot resolve `postgres`, it reaches the internet only through the proxy (`HTTPS_PROXY`), and the proxy refuses private, loopback and link-local addresses. Requests to `http://keyproxy:8080/anthropic/...` and `/openai/...` go to those APIs with the installation's key put on and whatever key or token the worker sent taken off. Codex runs billed to the API use that route (`ONE_CODEX_API_BASE_URL`); Rouh no longer hands the program the OpenAI key here (`ROUH_ONE_GETS_KEYS=0`).
- **No Docker socket** in any container. Every service restarts by itself (`unless-stopped`), drops every capability it does not need, has `no-new-privileges`, and has a health check.
- **The worker's volumes are always its own.** Docker copies an image's owners into a named volume only when the volume is new, so a `worker-home` made by an older stack as another user (Rouh for Mac's placeholder stack did, until 21 October 2026) stayed that user's, and the worker, which runs as 10001 and never as root, could not write its own home. So before the worker starts, the one-shot `worker-perms` (the workers image, as root with only `CHOWN` and `DAC_READ_SEARCH`, no network, `no-new-privileges`) gives `worker-home` and `one-run` to 10001 wherever anything in them is someone else's, and exits; the worker waits for it to finish (`service_completed_successfully`). The worker itself refuses to start with one sentence saying whose its home is if it still cannot write there.
- **Nothing is taken from the image's home.** An older volume hides the image's `/home/rouh`, its `.gitconfig` included, and without it git had no identity: the first start's commit failed ("Author identity unknown"), leaving an empty main and a clone with nothing in it, and the one program then logged "the workspace copy did not follow main" every minute. So the worker writes git's name, address and default branch into the volume's own `~/.gitconfig` whenever one is missing (keeping what the person set), and checks the runs' workspace on every start: main must have a commit and the workspace must be a checkout of it with one too. One that is not is made whole (a main with no workspace is cloned, a workspace whose main was lost becomes main), in a folder of its own and moved into place only once every step worked; anything found in the way is moved aside with the time in its name, never deleted.
- **Rouh talks to the one program** over its socket in the shared `one-run` volume, with the device token the worker writes there when it pairs on its first start.

## What works, and what does not yet

Since 29 October 2026 this is not kept here: `CONTAINERS.md` at the top of the repository is the one list of every feature Rouh has and whether this stack carries it, each with how it is checked, and the stack test (`tests/stack/`) checks every row marked works on every push to main, on Intel and Arm.

What changed in the stack that day, each with the reason:

- **Runs reach Rouh.** Rouh's internal addresses answered the same machine only, and the runs are in the worker. Rouh makes a key at its start in the volume the two share (`rouh/workerkey.py`), and a caller that shows it is let in as one on the same machine would be, never through a proxy and never through the relay.
- **The run screen and terminals.** There is no nginx here, so the core passes `/one/...` and `/one/ws` to the one program itself (`rouh/onebridge.py`), only for somebody signed in to Rouh, with a browser device the worker pairs for Rouh's page; the person's own cookies never reach the worker.
- **One workspace.** Its main is a bare repository in the `workspace` volume, which only the core writes; the worker reads it, and a run's work is handed to the core as a git bundle and landed there with land.sh (`bin/rouh-land`, `rouh/workspace_follow.py`). A repository both could write would let a run plant a git hook the core then runs, beside its keys. When the owner names a repository of their own (`ROUH_WORKSPACE_REMOTE`), main is kept level with it both ways.
- **Rouh changing its own code.** A run in a clone of `/code` hands its commits to the protected core the way `rouh-propose` does, so `./land.sh` in a run works here unchanged (`ROUH_LAND_THROUGH`); `assistant_job`, `check_tasks` and `improve_myself` are offered wherever the one program is paired, not only beside the crew.
- **Runs reach the internet** with the worker's proxy settings, which the run's environment had lost, and **the owner's own servers** only as the host:port pairs listed in `ROUH_KEYPROXY_ALLOW`, through `rouh-connect` (ssh), one key per purpose (`rouh-ssh-key`).
- **Telegram and Brevo** come from the settings file; the one program's notes to the phone go through Rouh's own bot (`/internal/phone`), so the worker holds no bot token.
- **The read-only shell** runs its commands in the worker, which holds no key (`one/shell.py`); **the UPS** is read over NUT's own protocol (`ROUH_UPS`).
- **Each run's memory limit and a stop that ends everything** are kept by the one program from `/proc` where it cannot make a box per run (`one/runprocs.py`); the worker as a whole has `mem_limit`.
- **The browser is a container of its own.** The core holds the keys, so it runs no browser; the base keeps the live browser and the YouTube fallback browser off (`ROUH_BROWSER=0`, `ROUH_YOUTUBE_BROWSER=0`), and the stack file turns them on with `ROUH_BROWSER_REMOTE=ws://browser:9230/browser`. Every browser the core uses (the live browser the person watches and takes over, sign-ups, a page read once when web_fetch could not read it, a PDF of a page, a transcript) is a Playwright connection to the `browser` service: Debian's Chromium behind Playwright's own server (`guard/bin/rouh-browser-server`, the protected core's), as 10001 on a read-only root with only `/tmp` in memory, mounting nothing but the protected core's files, on the `browser` network with only the core and the key proxy, so its one way out is the key proxy, which refuses this machine and private networks. The logins stay sealed in the core's database; a PDF's page and its pictures are handed to the browser by the core (`page_pdf.FOLDER`). The stack check pins its entrypoint, user, rights, networks, volumes and environment.

Still true:

- **Jailing.** Runs work as the worker's one user with no bubblewrap jail; the container is the only fence. Chromium runs without its own sandbox, as Playwright starts it. Rouh's read-only shell is the exception: each of its commands runs in the worker under Landlock (`rouh/sandbox.py`, `one/shell.py`), files read-only and no TCP, held by the kernel, and with `ROUH_SANDBOX=required` nothing runs without it. Not bubblewrap: Docker's syscall filter keeps the namespaces it needs for CAP_SYS_ADMIN, and the stack check refuses any other filter, so it could not run in the worker (task 139, step 139-14).
- **Anything that needs a public address** - Google's sign-in and consent, Gmail push, the Stripe and meeting-library webhooks, a phone's microphone - needs the phone address (the relay) or a tunnel, and `ROUH_PUBLIC_URL` set to it.
- **The images are not signed** and have no attestations yet (98-06's plan for the release). They are published to ghcr.io, and both are public: `rouh-base` since 24 October 2026, `rouh-guard` since Petar made it so (task 139; an anonymous `docker pull` of it worked on 30 October 2026), so a Rouh instance installs with no GitHub token at all. The images of before 23 October 2026 (`rouh-core`, `rouh-workers`, `rouh-keyproxy`) and `rouh-code` stay private; only an app before 0.3.4 still needs them.
- **Leaving out** (98-05, WP10): Claude Code is not in any image; pillow-heif is built against Debian's libheif with only its decoders, not from the wheels with their GPL encoder; ParadeDB's `pg_search` (AGPL) is not in the database image, and Rouh uses its own word search without it.
